============================================================
WATER BILLING SYSTEM
DEPLOYMENT STRATEGY & RECOMMENDED INFRASTRUCTURE PLAN
=====================================================

1. OBJECTIVE

---

The deployment strategy is designed to support the complete lifecycle
of the Water Billing System:

```
Development
    |
    v
Integration
    |
    v
QA / Testing
    |
    v
Staging / UAT
    |
    v
Production
```

The production infrastructure is sized according to the number of
water meters being managed.

Initial target scale:

```
50 Meters
100 Meters
300 Meters
```

The architecture should remain horizontally scalable so that increasing
the number of meters does not require a fundamental redesign.

============================================================
2. APPLICATION ARCHITECTURE
===========================

Recommended initial architecture:

```
            +----------------------+
            |   Client / Admin UI  |
            +----------+-----------+
                       |
                       v
            +----------------------+
            |   Reverse Proxy /    |
            |   Load Balancer      |
            +----------+-----------+
                       |
                       v
            +----------------------+
            | Spring Boot Backend  |
            | REST API             |
            +----------+-----------+
                       |
         +-------------+-------------+
         |                           |
         v                           v
  +-------------+             +-------------+
  | Relational  |             | Background  |
  | Database    |             | Jobs        |
  +-------------+             +-------------+
         |
         v
  Billing / Invoice
  / Meter Data
```

The initial deployment should remain a modular monolithic Spring Boot
application rather than introducing microservices prematurely.

This keeps infrastructure, deployment and operational complexity low
while still allowing individual modules to be separated into services
later if scale or business requirements justify it.

---

## 3.1 LOCAL DEVELOPMENT

Purpose:

* Individual development
* Unit testing
* API development
* Debugging

Each developer runs the Spring Boot application locally.

Example:

```
Developer 1 -> localhost:8080
Developer 2 -> localhost:8081
Developer 3 -> localhost:8082
```

Each developer should use an isolated database/data directory.

Recommended:

```
Spring Boot
    |
    v
Local H2 Database
```

---

## 3.2 SHARED DEVELOPMENT

Purpose:

* Integration of all developers' work
* API integration
* Cross-module testing
* Early detection of integration problems

Code flow:

```
Developer Feature Branches
          |
          v
      Pull Request
          |
          v
        develop
          |
          v
   Shared Development
      Environment
```

---

## 3.3 QA / TEST

Purpose:

* Functional testing
* Regression testing
* API testing
* Billing calculation validation
* Assignment history validation
* Negative/error scenario testing

Only an integrated and review-approved build should be promoted
from development to QA.

QA should use a dedicated database and test data set.

---

## 3.4 STAGING / UAT

Purpose:

* Production-like validation
* Business acceptance testing
* Final deployment verification
* Release candidate validation

Staging should replicate the production architecture as closely
as practical.

Typical flow:

```
QA Approved Build
       |
       v
   Staging
       |
       v
   UAT Sign-off
       |
       v
  Production
```

---

## 3.5 PRODUCTION

Only approved release artifacts should be deployed to production.

Production should have:

* Persistent database
* HTTPS
* Reverse proxy / load balancer
* Application monitoring
* Centralized logging
* Database backup
* Health checks
* Rollback capability
* Environment-specific configuration
* Secrets management

============================================================
4. BRANCHING AND CODE PROMOTION STRATEGY
========================================

Recommended branch flow:

```
feature/*
    |
    v
  develop
    |
    v
release/*
    |
    v
  main
    |
    v
Production
```

Development rules:

1. Each developer works on a feature branch.
2. Changes are committed regularly.
3. Pull Request is created after completion.
4. Code review is performed.
5. Automated build/tests are executed.
6. Approved changes are merged into develop.
7. Integrated build is deployed to the shared environment.
8. QA-approved changes are promoted toward release.
9. Production deployment is performed only from an approved release.

7. IMPORTANT DATABASE RECOMMENDATION
====================================

H2 is suitable for:

* Local development
* Automated tests
* Assignment demonstration
* Small development environments

For production, PostgreSQL or another managed relational database
is recommended.

Reason:

* Better operational reliability
* Production-grade concurrency
* Backup and recovery support
* Monitoring
* Transaction management
* Better long-term scalability
* Managed database options
* Easier disaster recovery

The application should therefore keep the database configuration
environment-specific.

Example:

LOCAL:
H2

QA:
PostgreSQL / isolated test database

STAGING:
PostgreSQL

PRODUCTION:
Managed PostgreSQL

8. INFRASTRUCTURE SIZING
========================

The following sizing is recommended for the expected meter volumes.

capacity limits.

The actual infrastructure should be adjusted after observing:

* API requests per second
* Meter reading frequency
* Database size
* Concurrent users
* Billing batch duration
* CPU utilization
* Memory utilization

============================================================
13. BILLING BATCH DEPLOYMENT
============================

Billing generation is different from normal API traffic because
large billing runs can create CPU, database and I/O load.

Recommended approach:

```
API Application
      |
      v
Billing Generation Job
      |
      v
Process meters in batches
      |
      v
Generate Invoice
      |
      v
Generate Invoice Items
      |
      v
Record Success / Skip / Failure
```

For 300 meters:

```
DO NOT process all meters as one large transaction.
```

Instead:

```
300 meters
   |
   +--> Batch 1
   +--> Batch 2
   +--> Batch 3
   +--> ...
   +--> Batch N
```

The existing billing-generation-job and job-skip concepts support
this approach.

Benefits:

* Lower memory usage
* Smaller transactions
* Easier retry
* Failure isolation
* Better observability
* Easier operational recovery

============================================================
14. METER READING INGESTION
===========================

Meter readings should be treated separately from user-facing
billing requests.

Logical flow:

```
Water Meter
     |
     v
Reading Ingestion
     |
     v
Validation
     |
     v
water_meter_readings
     |
     v
Billing Calculation
     |
     v
Invoice
```

The reading ingestion layer should support:

* Validation
* Duplicate protection
* Timestamp validation
* Meter identification
* Idempotent ingestion
* Invalid reading rejection
* Auditability

The current ingestion-key / uniqueness strategy should be retained
to prevent duplicate readings from creating incorrect consumption.

15. SECURITY ARCHITECTURE
=========================

Production deployment should include:

```
HTTPS / TLS
      |
      v
Reverse Proxy
      |
      v
Spring Boot
      |
      v
Database
```

Security controls:

* HTTPS only
* Strong authentication
* Authorization by role
* Secure password hashing
* Session/token expiration
* Database credentials outside source code
* Secrets stored using environment variables or secrets manager
* Database not directly exposed to the internet
* Firewall/security groups
* Input validation
* SQL injection protection through parameterized queries/JPA
* Audit logging for important operations

============================================================
17. BACKUP & DISASTER RECOVERY
==============================

Production database should have:

* Automated daily backups
* Point-in-time recovery where supported
* Backup retention policy
* Periodic restore testing
* Off-instance backup storage

Recommended principle:

```
Backup is not considered reliable until restore has
been tested successfully.
```

For the billing system, historical invoices and meter readings
are business-critical data and should therefore be treated as
persistent data requiring backup.

23. ROLLBACK STRATEGY
=====================

Every production release should have a rollback plan.

Application rollback:

```
Current Version
      |
      v
New Version
      |
   Failure
      |
      v
Previous Version
```

Database migrations require additional care.

Flyway migrations should be:

* Versioned
* Forward-compatible where possible
* Tested before production
* Never manually edited after being applied

For destructive database changes, use a multi-step migration
strategy instead of immediately removing existing columns/data.

25. FINAL RECOMMENDATION
========================

The recommended deployment approach is deliberately proportional
to the expected workload.

50 METERS
-> Single application instance
-> Small managed PostgreSQL
-> Automated backups
-> Simple reverse proxy

100 METERS
-> Single larger application instance
-> Managed PostgreSQL
-> Optional second application instance for availability

300 METERS
-> Two Spring Boot application instances
-> Load balancer
-> Managed PostgreSQL
-> Automated backups
-> Centralized monitoring/logging
-> Containerized deployment

The application should remain a modular monolith initially.

Microservices, message brokers, caching layers and database
replicas should be introduced only when measured workload,
availability requirements or future business growth justify
their operational complexity.

This approach provides:

* Low initial infrastructure complexity
* Clear deployment separation
* Controlled promotion between environments
* Production-grade database persistence
* Horizontal application scalability
* Reliable billing batch processing
* Operational monitoring
* Backup and recovery
* A clear path from 50 to 300+ meters
